## 1. 项目目标与范围

第一阶段交付一个**本机运行**的中文在线问卷系统：注册登录、私有问卷管理、四种题型与
限制校验、可配置条件跳转与返回修改、匿名、防重复提交、截止与关闭、问卷级与题目级统计。
业务数据全部存于 MongoDB，不使用关系数据库，不使用现成问卷系统框架。

**范围内**：账号与权限隔离、问卷生命周期、题目与限制、条件跳转、答卷与统计、网页界面。

**范围外**：公网部署、管理员后台、密码找回、邮件通知、问卷模板、导入导出、图表美化、
提交后编辑、跨设备填写草稿。

第一阶段成果作为第二阶段的基础，代码结构、数据模型与测试基线全部保留，可在其上扩展。

## 3. 系统设计

### 3.1 架构

单进程 FastAPI 应用，同源提供 JSON 接口与中文网页；无队列、无缓存、无后台服务。

```
浏览器（中文网页 / 接口调用）
        │ HTTP
        ▼
路由层  main.py ── 接口路由 + 页面路由 + 登录鉴权 + CSRF 校验
        ▼
领域层  surveys.py    问卷生命周期：草稿 / 发布 / 截止 / 关闭
        questions.py  题目与选项、稳定标识、限制规整
        responses.py  有效路径重算、答案校验、答卷保存、匿名脱敏
        stats.py      问卷级与题目级统计
        ▼
基础层  db.py（连接与索引）· security.py（密码哈希）
        sessions.py（会话）· csrf.py（双提交令牌）· util.py（公共工具）
        ▼
MongoDB
```

### 3.2 模块职责

| 模块 | 职责 |
|---|---|
| `main.py` | 全部路由、请求模型、表单解析、鉴权依赖、模板渲染 |
| `surveys.py` | 创建草稿、发布校验、截止时间、关闭、按创建者隔离读取 |
| `questions.py` | 题型常量、稳定标识分配、限制字段规整、增删改序、规则规整 |
| `responses.py` | 有效路径计算、逐题校验、并发安全的答卷保存、匿名脱敏 |
| `stats.py` | 按题型汇总成功答卷的有效答案 |
| `sessions.py` | 随机令牌会话，HttpOnly Cookie，支持退出与过期 |
| `security.py` | pbkdf2 密码哈希与校验 |
| `csrf.py` | 双提交 Cookie 令牌的签发与比对 |

### 3.3 关键请求流

- **填写提交**：读取问卷 → 核验是否已发布 / 已关闭 / 已截止 → 从第一题按规则**重算有效
  路径** → 只校验路径上的题目 → 剔除路径外答案 → 以唯一索引保证不重复 → 保存答卷。
- **查看统计**：校验创建者身份 → 读取成功保存的答卷 → 按题型汇总 → 匿名问卷不含填写者。

## 4. MongoDB 设计

### 4.1 集合划分

四个集合，避免把所有数据塞进一个集合：

| 集合 | 内容 | 增长方式 |
|---|---|---|
| `users` | 账号 | 随用户增长 |
| `sessions` | 登录会话 | 随登录增长，可清理 |
| `surveys` | 问卷本体，**内嵌**题目、选项与跳转规则 | 随问卷增长 |
| `responses` | 每份答卷一个文档 | 随答卷增长 |

### 4.2 字段定义

**`users`**

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | ObjectId | 主键 |
| `username` | string | 唯一用户名 |
| `password_hash` | string | `pbkdf2_sha256$260000$<salt>$<digest>`，不存明文 |
| `created_at` | Date (UTC) | 注册时间 |

**`sessions`**

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | ObjectId | 主键 |
| `token` | string | 随机令牌（唯一），写入 HttpOnly Cookie |
| `username` | string | 所属账号 |
| `expires_at` | Date (UTC) | 过期时间 |

**`surveys`**

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | ObjectId | 主键；同时是分发链接中的 id |
| `owner` | string | 创建者用户名，用于权限隔离 |
| `title` / `description` | string | 标题与说明，发布后冻结 |
| `status` | string | `draft` / `published` / `closed` |
| `anonymous` | bool | 是否匿名；发布后冻结 |
| `allow_multiple` | bool | 是否允许同一账号重复填写；发布后冻结 |
| `deadline` | Date (UTC) \| null | 截止时间，可调整 |
| `closed_at` | Date (UTC) \| null | 关闭时间 |
| `questions` | array | 有序题目数组，顺序即作答顺序 |
| `created_at` / `published_at` | Date (UTC) | 时间戳 |

**`surveys.questions[]`（内嵌）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `qid` | string | 稳定标识，规则与答卷都引用它 |
| `type` | string | `single` / `multi` / `text` / `number` |
| `title` | string | 题干 |
| `required` | bool | 是否必答（仅在有效路径上生效） |
| `options` | array | `{oid, text}`，仅单选题与多选题 |
| `rules` | array | `{rid, condition, target}`，顺序即优先级 |
| `min_choices` / `max_choices` | int | 仅多选；固定数量用上下限相等表达 |
| `min_length` / `max_length` | int | 仅文本；按字符计数 |
| `min_value` / `max_value` / `integer` | number / bool | 仅数字 |

**`responses`**

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | ObjectId | 主键 |
| `survey_id` | ObjectId | 所属问卷 |
| `respondent` | string | 内部记录的填写者账号；**返回创建者前在服务端移除** |
| `answers` | array | 仅有效路径上的答案：`{qid, ...}` |
| `once` | bool | 是否受"每账号一次"约束，用于部分唯一索引过滤 |
| `submitted_at` | Date (UTC) | 提交时间 |

### 4.3 索引

```javascript
db.users.createIndex({ username: 1 }, { unique: true })
db.sessions.createIndex({ token: 1 }, { unique: true })
db.responses.createIndex(
  { survey_id: 1, respondent: 1 },
  { unique: true, partialFilterExpression: { once: true } }
)
```

最后一条是**部分唯一索引**：只有标记 `once: true` 的答卷进入索引，因此"禁止重复填写"
的问卷在数据库层保证同一账号最多成功一次；允许重复填写的答卷不带该标记，不受约束。
两个并发提交同时到达时，只有一个能插入成功，另一个收到重复键错误，由应用转换为 409。

### 4.4 为什么把题目内嵌进问卷

题目、选项与跳转规则**从不脱离问卷被单独查询或修改**：永远是"读整份问卷"或"改整份问卷"，
不存在"查询所有问卷的第 2 题"这类访问。既然总是整体读写，就整体存成一个文档：

- 一次读取即得到完整问卷，避免多集合联查；
- 写入天然原子，不会出现"题目加了一半"的中间状态；
- 发布后整份冻结，语义与存储结构一致。

### 4.5 为什么答卷单独成集合

答卷数量大、持续增长、需要独立扫描统计。若塞进问卷文档会导致单文档无限膨胀并拖慢写入。
答卷只增不改，独立集合配合索引即可支撑统计与重复校验。

### 4.6 为什么不用关系数据库结构

用关系模型需要 `surveys` / `questions` / `options` / `rules` 多张表，读一份问卷要多次
JOIN，而本系统的题目结构与问卷强绑定、无独立生命周期，JOIN 只带来复杂度。此外不同题型
的可选字段差异大（单选有选项、数字有范围），在关系表中需要大量可空列或额外表，在文档中
可以自然表达。

### 4.7 稳定标识

题目 `qid`、选项 `oid`、规则 `rid` 均为稳定标识，规则与答卷都引用**标识而非显示序号**。
因此调整题目顺序、增删选项不会让既有规则错位。

## 5. API 说明

启动后访问 `/docs` 可查看可交互的 OpenAPI 文档。网页路由与接口共用同一套领域逻辑。

### 5.1 鉴权与错误约定

- 需登录而未登录：`401`；
- 访问不属于自己的问卷、或问卷不存在：统一 `404`（不泄露存在性）；
- 修改已冻结内容、已关闭 / 已截止的提交、重复提交：`409`；
- 请求体校验失败：`400`，中文提示并定位到具体题目。

## 6. 关键逻辑说明

### 6.1 跳转设计

每条规则由「触发条件」与「跳转目标」组成，挂在题目上，按数组顺序保存。

| 题型 | 支持的条件 |
|---|---|
| 单选 | 选中指定选项（`is`） |
| 多选 | 包含任一指定选项（`any`）／包含全部指定选项（`all`） |
| 数字 | 等于（`eq`）／大于（`gt`）／小于（`lt`）／含两端的区间（`between`） |

**匹配与路径**：服务端从第一题逐题推进，取当前题命中的**第一条**规则；有规则则跳到目标，
无规则则进入下一题；命中"结束"则停止。这条推进链就是**有效路径**。

**只可向后**：目标只能是后面的题目或结束。由于规则不允许指向前面的题目，"形成循环"必然
包含一条反向边，因此发布校验只要拒绝"目标索引不大于当前题索引"即可同时杜绝回跳与循环，
无需额外做环检测。发布校验还会拒绝指向已删除题目、引用已删除选项的规则。

**返回修改**：路径改变后，新路径不再经过的题目，其答案在提交时被剔除，既不保存也不参与
统计。服务端始终从第一题重算，**不信任客户端声称的路径**——即使客户端伪造一条路径外的
答案，也会被丢弃。

**跳过必答**：必答只在有效路径上生效，被跳过的必答题无需填写。

### 6.2 校验设计

| 题型 | 限制 | 提交时校验 |
|---|---|---|
| 单选 | 选项集合 | 答案必须是本题的有效选项；可选为空放行，必答为空拒绝 |
| 多选 | 最少 / 最多选择数 | 答案是不重复的有效选项集合；上下限相等时要求数量精确相等 |
| 文本 | 最少 / 最多字数 | 按**字符**计数（非字节），空串视为未填 |
| 数字 | 最小值 / 最大值 / 是否整数 | 只接受**有限**数值，拒绝布尔值、`inf`、`nan`；校验范围（含两端）与整数要求 |

不属于该题型的限制字段在写入时丢弃，避免脏数据混入。

**发布校验**：至少一道题；每题有题干；选择题至少两个选项；限制配置不得自相矛盾（上下限
倒置、负数、最少选择数超过选项总数等）；所有跳转规则目标合法。

**错误定位**：返回 `{"detail": {"message": ..., "errors": {qid: "第 N 题…"}}}`，页面在
对应题目下方显示中文提示。

### 6.3 并发与防重复

"先查有没有提交过、再插入"在并发下会失效（两个请求可能同时查到"没有"）。因此改为**数据库
约束兜底**：对禁止重复的答卷写入 `once: true`，由 `(survey_id, respondent)` 的部分唯一
索引保证只有一个插入成功。真实并发测试用两个线程经 `threading.Barrier` 对齐后同时提交，
结果恰为 `201` 与 `409`，答卷只有一份。

### 6.4 匿名脱敏

匿名与否只影响**返回给创建者的内容**。答卷文档内部始终记录 `respondent`，用于执行重复
限制；在序列化返回前由**服务端**移除该字段。客户端隐藏字段不构成匿名保障。

### 6.5 生命周期与截止

状态为 `draft → published → closed`，关闭是终态，不提供重开。

- 发布后标题、说明、题目、选项、跳转规则、匿名与重复配置**一并冻结**，仅可调整截止时间或关闭；
- 截止时间统一存 **UTC**，网页按本地时间展示；
- `now >= deadline` 即不可提交（截止瞬间含在内）；
- **打开填写页与每次提交都重新核验**状态，因此"填写中途被关闭"的提交仍会被拒绝。

### 6.6 统计口径

统计只覆盖**成功保存的答卷**及其**有效答案**：

- 被跳过的题、未填的可选题不计为回答；空文本不计入文本题；
- 数字无回答时平均值为空（界面显示"暂无（无回答）"），**不显示为零**；
- 路径外答案在提交时已被剔除，因此不进入统计；
- 允许重复填写时，每份答卷分别计数；
- 统计只对创建者开放，输出不含填写者身份。

| 题型 | 统计字段 |
|---|---|
| 单选 | 有效回答总数、各选项人数 |
| 多选 | 有效回答总数、各选项被选次数（一份答卷同一选项只计一次） |
| 文本 | 全部填写内容 |
| 数字 | 有效回答总数、平均值（无回答为 null） |

## 8. 遇到的问题与解决

| # | 问题 | 现象 | 原因 | 解决 |
|---|---|---|---|---|
| 1 | 网页只能建两个选项 | 单选 / 多选在网页上最多填 2 个选项，课程示例的 3 个选项建不出来 | 新增题目表单在模板里写死两个输入框，而接口层本无上限 | 为新增与编辑表单都加「添加选项」控件；编辑时新行带空 `oid`，由服务端分配标识，原有选项标识不变；空白行提交时丢弃 |
| 2 | 注册后丢失返回地址 | 从问卷链接进入、注册新账号后，登录成功跳到"我的问卷"而不是原问卷 | 注册流程未在登录页、注册页与导航之间传递 `next` | 全链路保留 `next`，注册与登录错误重试也不丢失；继续只接受站内相对地址，防开放重定向 |
| 3 | 已发布问卷看不到题干 | 发布或关闭后，管理页只剩选项与控件，题目本身不可见 | 编辑页模板的只读分支遗漏题干渲染 | 只读展示题干并保持模板转义，不重新开放编辑 |
| 4 | 并行开发测试互相清库 | 两条开发线同时跑测试时出现大量假失败 | 多个工作副本共用同一个测试库，每个用例前都会清空它 | 测试库名改为可用环境变量覆盖，各副本使用独立库名，默认值不变 |
| 5 | 两路改动合并冲突 | 题型线与生命周期线同时修改了答卷模块与说明文档 | 都触及"提交前校验"与 README | 逐处按语义合并：导入两边都保留，说明文档取超集；合并后核对测试数量，确认未丢用例 |
| 6 | 规则顺序无法调整 | 跳转规则只能逐行重填，无法调整优先级 | 编辑页只渲染规则行，没有排序控件 | 增加每条规则的上移 / 下移按钮，数组顺序即优先级；补测试证明调整后生效顺序确实改变 |
| 7 | 实现一度偏离既定工作流 | 最初直接在主干顺序开发，未按约定的分支与子任务编排 | 未先核对工作流原文 | 核对原文确认偏离，改为「集成分支 + 独立工作副本 + 完成后再统一审查」的编排，保留首个红绿循环作为基线 |
| 8 | CSRF 覆盖范围存疑 | JSON 接口未校验 CSRF 令牌 | —— | 实测确认表单编码与 `text/plain` 请求被拒（422）且无副作用；跨站表单无法构造 `application/json`，风险已被内容类型挡住。以测试固定该行为，不为此破坏既有接口契约 |

## 9. AI 使用过程

### 9.1 使用工具

Claude Code（命令行 AI 编程工具），配合 Git 与本地 MongoDB。工作方式为：人工确认业务
规则与关键取舍，AI 负责规格、实现、测试与文档，过程记录在仓库的 Git 历史与开发记录中。

### 9.2 使用的工作流技能（Matt 技能套件）

本项目采用 Matt Pocock 的工程工作流，把"从需求到交付"拆成澄清、规格、拆分、实现四个
阶段，每个阶段由一个具体技能承载，实现阶段内部再调用测试与审查技能。

| 阶段 | 技能 | 实际做法 | 产物 |
|---|---|---|---|
| 澄清 | `grill-with-docs` | 用具体例子把业务问题讲清楚，逐轮请用户拍板；把确认后的术语固定下来 | 需求决策、术语表 |
| 规格 | `to-spec` | 生成 30 条用户故事、技术方案、测试范围；先标 `draft`，获批后才转 `approved` | `spec.md` |
| 拆分 | `to-tickets` | 把 7 项可演示交付写成**任务图**，显式声明阻塞关系，而不是一串步骤 | `issues/01`–`08` |
| 实现 | `implement-spec` | 见下方九步 | 集成分支与提交历史 |
| 测试 | `tdd` | 每个用户行为一个红→绿循环 | 18 个测试文件、218 例 |
| 审查 | `code-review` | 两条独立轴并行审查 | 审查结论与修复 |

**implement-spec 的九步，本项目的实际执行：**

1. **读规格与工单，理解任务图。** 任务依赖为 01→02→03→04→06、02→05、05+06→07，
   由此算出"前沿"——每一步当前能开工的工单集合。
2. **探索**（可选步骤）：本项目跳过，规格已足够明确。
3. **建集成分支** `integration/mongodb-survey-phase-one`，所有工作最终汇到这里，主干不动。
4. **每个可执行工单派一个实现子代理**，每个子代理：
   - 拥有**独立 worktree + 独立分支**，开工前确认基线是集成分支；
   - 先读 `tdd` 技能原文，再按"一个行为一个红绿循环"实现；
   - 约束写明：只打在 HTTP 接缝、不得直接查库断言、不得一次写完所有测试；
   - 完成前把集成分支最新提交合并进自己的分支。
5. **每完成一张工单，派一个合并子代理**把它合入集成分支，并在合并结果上跑全量测试、
   核对改动统计与被合并分支一致，防止丢用例。
6. **前沿变化就继续派发。** 工单 02 完成后，03 与 05 同时就绪，两者**并行开发**；
   为避免测试库互相清空，先把测试库名改为可用环境变量覆盖，各自使用独立库。
7. **全部完成后在集成分支跑 `code-review`**：以开工前的提交为固定基准点（53 个文件、
   约 8400 行改动），**Standards 轴**检查是否符合仓库成文标准与常见代码坏味道，
   **Spec 轴**检查是否忠实实现规格；两轴各起一个子代理，互不参考对方结论。
8. **审查发现的问题由一个子代理统一修复**，而不是各改各的。
9. **清理全部实现子代理的 worktree**，只保留集成分支作为交付物。

**`tdd` 的实际做法与真实记录：**

- 接缝确定为 **HTTP 接口层**，明确"测试通过接口观察行为，不直接查询数据库"；
- 第一个红绿循环：先写 `POST /api/register` 应返回 201 的测试，运行得到
  `assert 404 == 201` —— 失败原因是**接口尚未存在**，而不是数据库连不上（这一点被特意
  检查，避免把环境故障当成业务失败）；随后只写刚好够用的实现，测试转绿；
- 之后每个行为重复该循环，严格避免两种反模式：**先写完全部测试再写实现**，以及
  **绕到数据库去断言**；
- 不足如实记录：有两个切片（错误密码兜底、越权隔离）在写测试时已随前一片实现变绿，
  未经历独立红阶段，其余行为均为红→绿。

**`code-review` 的实际收获：**

- **Spec 轴**发现 2 处真缺口：规则顺序调整控件缺失（工单要求"调整规则顺序"，实现只能
  逐行重填）、JSON 接口的 CSRF 覆盖存疑；
- **Standards 轴**发现 4 处问题：标识转换函数在四个模块重复、字段取值访问器三份实现、
  测试辅助函数在约 15 个文件重复、题型分派散落六处；
- 另有 1 条结论经核对为**误报**（审查者把基准提交里已存在的工单文件误判为未提交），
  被核实后剔除，未带入修复；
- 修复结果：补齐排序控件、记录 CSRF 的内容类型防护决策、抽取公共工具、收敛测试辅助
  函数；题型分派经判断职责各异，**不强行合并**以免制造耦合。测试由 200 例增至 203 例。

**任务管理技能：** 另用 `task` 与 `update-scope` 两个技能维护任务看板与进展时间线，
记录每一步的真实状态、证据与阻塞，供后续接手者查阅。

**一次偏离的如实记录：** 实现初期曾在主干上顺序开发，未按上述编排执行。主控质疑后，
对照 `implement-spec` 与 `matt-development-flow` 原文核实，确认偏离成立——宿主具备分派
子代理的能力、项目也具备使用 worktree 的条件，原执行条件本已满足。随后按主控决定改回
原版编排，并保留已完成的第一个红绿循环作为基线。

### 9.3 提示词与生成结果（真实节选）

**示例一：需求澄清**

```
Prompt：多选的条件跳转，你希望支持"选了其中任意一个"还是"必须全部选中"？
        数字题的条件，是等于某个值，还是大于/小于某个值，还是一个区间？
结果：用户确认"任一 / 全部"两种多选条件，以及等于、大于、小于、闭区间四种数字条件。
修改：据此在规格中固定为六种条件形态（单选 1 种、多选 2 种、数字 4 种）。
```

**示例二：规格与任务拆分**

```
Prompt：根据已确认的业务规则，生成规格（用户故事 + 技术方案 + 测试范围）并拆成有依赖
        关系的交付任务，每项要可独立演示、可独立验收。
结果：生成 30 条用户故事与 7 项任务拆分，依赖图为 01→02→03→04→06、02→05、05+06→07。
修改：主控核对后补充"失效答案不提交、不保存"的验收措辞，统计排除效果改由第 6 项验证。
```

**示例三：实现（测试先行）**

```
Prompt：你是实现子代理。先读 tdd 技能原文，一个用户行为一个红→绿循环，测试只打在
        HTTP 接缝上，不得直接查数据库断言，不得一次写完所有测试再写实现。
结果：生成题目、答卷、校验模块与 44 个 HTTP 测试，测试数从 29 增至 73。
修改：主控在验收前发现网页只能填两个选项，追加一次修复切片（见问题 1）。
```

**示例四：独立审查**

```
Prompt：从"是否符合仓库成文标准"与"是否忠实实现规格"两个独立角度审查这批改动，
        分两路并行，互不参考对方结论。
结果：发现 2 处规格缺口（规则顺序调整控件缺失、JSON 接口 CSRF 覆盖存疑）与 4 处重复代码。
修改：补齐排序控件；CSRF 经实测确认由内容类型防护挡住，记录决策而不改接口契约；
      重复的标识转换与字段取值工具抽到公共模块。
```

### 9.4 AI 做错了什么

## 10. 已知限制与第二阶段扩展点

- 统计查询未单独建立 `survey_id` 索引（当前规模不构成问题）；
- 会话过期由应用判断，未使用 TTL 索引；
- 网页截止时间按服务器本地时区折算 UTC，多时区部署需改为客户端提交偏移；
- 关闭为终态，无重新开放；
- 统计允许查看草稿问卷（返回空统计）；
- 第一阶段不做跨设备填写草稿，已提交答卷不提供修改。

以上均可作为第二阶段需求变更的扩展入口，现有集合结构、稳定标识与测试基线无需推倒重来。
